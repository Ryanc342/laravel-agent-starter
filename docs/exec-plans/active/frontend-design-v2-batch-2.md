# Frontend design v2, batch 2: eleven more page patterns, real bulk actions, import and export

## Purpose
Give AI agents a pattern, a demo and, where it matters most, a working example for the eleven batch 2 pages (search results, multi-step wizard, approval flow, list beside detail, detail with tabs, bulk actions, import / export, print page, charts and reports, calendar, kanban), so these pages come out right the first time; and close the batch 1 leftovers.

## Agreed decisions
From grilling rounds 12 to 14 (Q68 to Q91) on the user's Q&A page, 2026-11-14:
1. Q68: all eleven patterns in this one plan.
2. Q69: the reference task feature (`docs/reference/tasks`) gets real bulk actions, import and export, frontend and backend, with tests. The other patterns are frontend demos on /style fed through props (Q33).
3. Consequence, raised to the user with the plan: a server PDF (decision 16) needs a backend, so the reference task feature also gets a print page of one task with "Print" and "Download PDF". Invoices and receipts stay project work; the /style demo shows the invoice layout.
4. Q70: the sign-in pages keep the label above the input (the one exception to Q17, already in `patterns/auth.md`). No change.
5. Q71: a signed-in user who opens a URL that matches no route sees "Go to dashboard", not "Log in": the 404 for an unknown URL runs the web middleware (a fallback route), so the session is read.
6. Q72: the leftovers that need no new page are done here (M10); the array-style field names and the amount unit wait for the first page that needs them; the welcome page waits for batch 3.
7. Q73: /style stays in the production build. Checked: it is a dynamic chunk (`isDynamicEntry` in `public/build/manifest.json`), not imported by `app.tsx`, so a user downloads it only by opening /style, which answers 404 outside local.
8. Q74, Q88, changed by the user after the plan was written: the Claude Code reviewer is pinned to `model: opus` in `.claude/agents/reviewer.md`, and the Codex reviewer to `model = "gpt-6.1-sol"` in `.codex/agents/reviewer.toml`. The user asked for "sol"; OpenAI's Codex docs (learn.chatgpt.com/docs/models and docs/agent-configuration/subagents) give `gpt-6.1-sol` as the Sol model ID and as the model of their example reviewer, and document no short alias. Reasoning effort is not set, so both reviewers keep the parent's.
9. Q75, Q91: search is a box in the top bar; Enter opens a search results page with the results grouped by type and the matched text highlighted. The box is a shared block shown in the /style demo and the pattern, not mounted in the app layout until a project has something to search.
10. Q76: a multi-step wizard is its own page with the steps listed on the left; it is the exception to Q28 (long forms in a dialog). "Next" checks the fields of the current step. On a phone the step list becomes one line at the top ("Step 2 of 3 · Team").
11. Q77: an approval page puts Approve and Reject to the right of the title, with the other actions; below, a timeline says who did what and when. Reject asks for a reason in a dialog.
12. Q78: list beside detail: on a computer the list takes about a third of the width on the left, the selected row uses the selected (press) colour and its id is in the URL; on a phone the list comes first and a row opens the detail as its own screen with a back link at the top left.
13. Q79: tabs are the pill style (a grey strip, the selected tab a white block), shadcn `Tabs`. The selected tab is in the URL (like rows per page); on a phone the strip scrolls sideways.
14. Q80: ticking rows shows a bar floating at the bottom of the page ("2 selected · Complete · Delete · ✕"), visible while scrolling. The header checkbox selects the rows of this page; then a line offers "Select all N results". Delete asks in a dialog. On a phone each card has a checkbox.
15. Q81, Q90: import is upload then import: an "Import" dialog takes a CSV file (with a "Download template" link); the backend checks every row; if any row has an error nothing is imported and the errors come back as toasts, at most five ("Row 3: Due date is not a date"), plus one "And N more errors" when there are more. Success is one toast ("Imported 41 tasks").
16. Q82, Q83, Q89: files are CSV only. Export downloads the list as the user sees it (same search, sort and filters), all pages, UTF-8 with a byte order mark so Excel shows non-English text. A print page prints with the browser (app chrome hidden, A4) and also offers "Download PDF", made on the server by `spatie/laravel-pdf` with the DOMPDF driver (pure PHP; no flexbox or grid, so the PDF view is laid out with tables). The driver is one line in `.env` (`LARAVEL_PDF_DRIVER=dompdf`).
17. Q84: a report page has a row of number tiles and charts below; the range is a row of presets (7 days, 30 days, 90 days, Custom with two dates) and lives in the URL. One series is `chart-1` (the primary blue); several series take `chart-1` to `chart-5` in that fixed order and always have a legend.
18. Q85: the calendar is a month view only; an event opens in a dialog (Q20); on a phone the month becomes a list ordered by date.
19. Q86: every date field uses one shared date picker (shadcn `Calendar` on react-day-picker in a `Popover`), the same in every browser; it reads and writes `YYYY-MM-DD`, so URLs and requests do not change. Number fields stay number inputs.
20. Q87: a kanban board shows its columns side by side; on a phone the columns scroll sideways, each a little narrower than the screen so the next one shows. Cards move by dragging (dnd-kit, keyboard included) or with a "Move to" menu on each card.
21. Dependencies (Q34, Q79, Q89): `@radix-ui/react-tabs`, `react-day-picker`, `recharts`, `@dnd-kit/core` and `@dnd-kit/sortable` (plus `@dnd-kit/utilities` only if the sortable code needs it); `spatie/laravel-pdf` and `dompdf/dompdf`. Nothing else is added or upgraded.
