# Frontend design v2, batch 3 feedback: action buttons on the right, the /style console warning, English and Chinese

## Purpose
Put every button that acts on a page, a form, a dialog or a step at the right end of its row; remove the React warning the /style page logs; and let every user switch the whole app between English and Simplified Chinese, with checks that keep every new sentence translated.

## Agreed decisions
From the user's review of batch 3, 2026-11-14 (four screenshots: the task page's Complete / Edit / Delete under a long title on the left, the wizard's Next, the print page's Print / Download PDF, the settings Save, all on the left; "按钮全部统一放右边比较好，剩下的都没什么问题了"; then "顺便做中英切换，`/style` 页的小警告也一起处理，加进这个计划里") and grilling round 16 (Q96 to Q102):

Buttons
1. A row of action buttons sits at the right end of its row: the actions of a page or record header, the buttons at the end of a form, a dialog, a wizard step or a settings form, and a toolbar of actions above content (Print / Download PDF, Import / Export). In a header whose title wraps, the actions stay on the right (on their own line, aligned right), never under the title on the left.
2. Consequence, raised to the user with the plan: with the row on the right, the main button is the rightmost one: Cancel (or Back) first, then the main button. This turns round `form.md`'s "the main one first, then Cancel". On a phone, the buttons of a form, a dialog or a wizard step stay full width and stacked, with the main button on top.
3. Not action rows, so they stay as they are: the sign-in pages (full-width button, `patterns/auth.md`), the centred empty and error states (Q53), the landing hero's buttons (they follow the hero text), and controls that are not actions on the content: pagination, menus, tabs, the public bar, the kanban columns, the month calendar's navigation and the floating bulk action bar.

The /style warning
4. The React warning batch 3 found in the browser console of `/style`, attributed to `UiFieldsDemo` and not investigated, is traced to its cause and fixed there, not silenced.

English and Chinese
5. Q102, Q97: two languages, English (`en`) and Simplified Chinese (`zh_CN`). A first visit follows the browser's `Accept-Language`: any Chinese (`zh`, `zh-CN`, `zh-TW`, ...) gives `zh_CN`, anything else `en`. This replaces Q30 ("English by default"), which was answered before a switch existed.
6. Q98: the language is, in this order, the signed-in user's choice (a new nullable `locale` column on `users`), the `locale` cookie, the browser's, then `en`. A `SetLocale` middleware in the web group applies it before the Inertia middleware; `<html lang>` already follows `app()->getLocale()`.
7. Q96: on Settings → Appearance a "Language" choice next to the theme (a `ToggleGroup`: "English" and "中文", each named in its own language); on the guest pages (the public bar and the sign-in pages) an "EN / 中文" switch at the top right. Both call one route (`locale.update`, a FormRequest allowing `en` and `zh_CN`) that saves the choice on the user when signed in, sets the cookie always, and redirects back, so the page comes back in the new language.
8. Q100: one source, Laravel's language files, and no package. A sentence is keyed by its English text (`lang/zh_CN.json`: `"Save changes": "保存更改"`), so English needs no JSON file. Laravel's own groups (`validation`, `auth`, `passwords`, `pagination`) are published with `php artisan lang:publish` and get `lang/zh_CN/*.php`, with validation `attributes` so field names read in Chinese. React receives the current language's strings in a shared Inertia prop (sent once per page load if Inertia v3 offers once props; record which) and translates with `t(key, replace)` and `tChoice(key, count, replace)` from `resources/js/lib/i18n.ts`, which follow Laravel's `:name` placeholders and plural syntax.
9. Q99: everything the user reads is translated: React text (labels, buttons, headings, states, `aria-label`s, toasts written in React), backend text (toasts, validation messages, notifications, mails including Laravel's own verify-email and reset-password mails, the task PDF), and formats: dates and numbers through `Intl` with the current language (`lib/format.ts`, `formatMoney`), and the `DatePicker`'s month and day names from `react-day-picker/locale` (`zhCN`; the installed react-day-picker 10.0.2 exports it). What users type (a task's title) is not translated.
10. Consequence, raised to the user with the plan: a notification today stores its finished sentence when it is sent (`app/Notifications/*`: `'message' => __(...)`), so it would stay in the language of the moment it was sent. It stores the English sentence and its values instead, and `NotificationResource` translates them in the reader's language when shown.
11. Q101: `composer check` fails on a missing translation. A new structure test (`tests/Structure/TranslationsTest.php`) collects every key used in `t()`, `tChoice()`, `__()`, `trans()`, `trans_choice()` and `@lang` in `app`, `resources`, `routes` and `docs/reference/tasks`, and fails when `lang/zh_CN.json` or the `lang/zh_CN` group has no entry for it, or has an entry no code uses. A lint rule in `lint/oxlint/ezdev.js` fails on text a user reads written straight into JSX (text children, and the `title`, `placeholder`, `aria-label`, `label` and `alt` props) instead of through `t()`. Exempt: the /style page's own section titles and specimen labels and the example data its demos receive, because /style is a development tool and stays English; the components it shows are translated.
12. Docs: a new `docs/rules/translations.md` (write a sentence in English through `t()` or `__()`, add its Chinese in the same commit, never translate user content), its row in the AGENTS.md table (AGENTS.md has 92 of its 100 lines), `docs/rules/frontend.md` (strings through `t()`), `docs/design/foundations.md` (language and copy in both languages), and a `[review]` rule in principle 10 of `docs/golden-principles.md`.
13. Tests run in English (no `Accept-Language`, no cookie), so existing assertions do not change. If one would, stop and ask the user.

## Surprises & Discoveries
- `detail.md` already says the header's actions are "on the right", but the header row is `flex flex-wrap justify-between`: when a long title takes the line, the actions wrap to the next line and start on the left.
- `ResponsiveDialogFooter` is `sm:justify-start`, so every dialog's buttons sit on the left on a computer.
- A search for flex rows that hold buttons without `justify-end` found 18 places; besides the files M2 names they are pagination, the kanban, the month calendar, the public bar, the bulk bar, the hero and the sign-in pages (decision 3).
- There is no `lang/` folder, no `locale` on users and no translation in React; `config/app.php` has `locale` `en`; the font stack already falls back to PingFang SC, Microsoft YaHei and Noto Sans SC; cookies other than `appearance` and `sidebar_state` are encrypted.
- Notifications store `'message' => __(...)` when sent (`AccountCreated`, `EmailChanged`, `PasswordChanged`).
- The app has no SSR bundle (`bootstrap/ssr` is empty), and `UiFieldsDemo` shows no obvious invalid nesting in its source.
