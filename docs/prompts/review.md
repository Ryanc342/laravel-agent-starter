# Review prompt

Used by the two reviewer subagents, `reviewer-opus` and `reviewer-haiku` (.claude/agents/), or pasted into a new conversation.

The session that asks for a review names one lane and the round, for example: `Lane: tests. Round: 3. Plan: docs/exec-plans/active/<feature>.md.` There is no review between milestones: every round is a round of the final review. The rounds of a plan are numbered 1, 2, 3, and each runs both reviewers at the same time on the same commit, with the same round number; a lane is reviewed until it is done (docs/workflow.md, step 4). The lanes `look` and `behaviour` come last, in the final review only, and name the address of the reviewer's seat: `Lane: look. Round: 3. App: http://localhost:8101. Plan: docs/exec-plans/active/<feature>.md.` The lanes and the places that touch them are in docs/golden-principles.md, "Review lanes". One run reviews one lane; a change that touches three lanes needs three runs.

---

You did not write this change. Review it with fresh eyes against its plan, for one lane.

Bash runs only the git commands that read: `git diff`, `show`, `log`, `status`, `ls-files`, `ls-tree`, `rev-parse`, `rev-list`, `merge-base`, `cat-file`, `grep`, `blame` and `describe`, alone, joined with `&&` or `;`, or piped into `head`, `tail`, `grep`, `wc`, `sort`, `uniq`, `cut`, `cat`, `tr` or `sed -n '<lines>p'`. A hook (scripts/hooks/reviewer-commands.php) refuses every other command before it runs, says why, and logs the refusal: a redirection, `tee`, a substitution, `xargs`, `awk`, `sed -i`, any other program. Read files with Read, and search them with Grep and Glob.

1. Read the lane and the round from the request. If either is missing, or the lane is not one of `business`, `input`, `frontend`, `tests`, `look`, `behaviour`, stop and end with the result line below with lane `none`.
2. Read the plan in `docs/exec-plans/active/` (or the file the request names). Its "Agreed decisions" are the specification.
3. Read the plan's diff: everything since the commit before the plan was added, the base the finish check uses too. `git log --diff-filter=A --format=%H -- <plan path>` gives the commit that added it (use the last line if there are several; for a plan moved to completed/, also ask for its path in active/); then `git diff <that commit>^`, plus untracked files from `git status`. A plan that is not committed yet: `git diff HEAD` plus untracked files. Never diff against `main`: that shows changes that are not the plan's.
4. Read the lines that start with `Accepted:` in the plan's Decision Log and in docs/exec-plans/tech-debt.md. Each quotes the user's answer to a question a review raised. Do not report what an `Accepted:` line covers.
5. Read docs/golden-principles.md and the "Code Review Rules" section of AGENTS.md. The `[review]` rules of your lane are yours: no machine checks them. The machines check only the 18 `[PHPStan]`, `[oxlint]` and `[Structure]` rules; if the change breaks one of those anyway, report it as P1 and say which check missed it.
6. For each agreed decision that falls in your lane, find the file and method that implement it.
7. Lanes `look` and `behaviour` only: if the change touches resources/js, resources/css, resources/views, lang, DESIGN.md or docs/design, look at the screens. The builder has run `scripts/screen-round` (with `--reference` when the change touches docs/reference/tasks/: then both seats are copies with the reference feature installed), which reset the database of your seat to its seeded state (docs/workflow.md, step 4): it holds only the test accounts. With your own isolated headless Playwright MCP server (`playwright` for `reviewer-opus`, `playwright-review` for `reviewer-haiku`), open the app at the address the request names (`App: <url>`; without one, APP_URL in .env), which runs the code of the commit under review; log in as test@example.com with the password `password` from database/seeders, or the account the plan's Progress names for a role). Lane `behaviour`: walk every item of the plan's walk list (under Validation: `W1 <role>: <flow>`) through the app's forms, from its first step to its last, as that role; a step that fails (an error page, a refusal the plan does not give, a missing button) is P0. A plan with no walk list: number the flows yourself at the top of your report, one line per flow the plan's decisions add or change and per role it names (`W1 <role>: <flow>`), and walk those. Report one line per item: `W1 walked`, or `W1 not walked: <reason>` for an item you did not try. An item walked up to a step that failed is walked, and the failed step is the P0. The pages to look at show the data that walk made: never add rows any other way. Then open every page the change adds or changes. Take temporary screenshots at 1280×800 and at 390×844, and one in dark mode (Settings, Appearance), without specifying filenames. Also open the style overview page (`/style`, development only) and compare each changed page with the pattern demo and the component demos there: a page that looks different from its pattern's demo, with no reason in the plan, is a finding. Check your lane's `ui` rules of principle 10 before closing the browser, and set Appearance and Language in Settings back to what they were when you logged in; `browser_close` removes those temporary files. Close the browser even on error; the launcher also closes it after tool errors. Every file the browser tools save, also under a file name or a path you give them, stays in the browser's temporary folder (scripts/playwright-mcp) and is removed when the browser closes: nothing you save reaches the project folder. If the user explicitly asks to keep a screenshot, say so in your report and the builder takes it. If the app is not running or a page cannot be reached, report `[P1] app not running: <page> not checked` instead of guessing.
8. List every `[review]` rule of your lane that the change touches (it adds or changes code the rule is about), in the order docs/golden-principles.md lists them, each with `ok` or the finding. Every touched rule counts the same. Leave out the rules it does not touch, and the rules of other lanes.
9. Report P0 and P1 findings, each as `[P0|P1] path:line`, what is wrong, the rule it breaks, and which owner should hold it. A finding only the user can settle (two rules that disagree, a default the plan does not give, a deviation from a pattern) ends with `(for the user)`: the builder asks the user in the same round (docs/workflow.md, step 3).
    - P0: wrong behaviour, data loss, a permission hole, a decision implemented differently from the plan.
    - P1: a `[review]` rule of your lane broken in the changed code, behaviour not in the plan, or a missing or weakened test.
10. Then one line on the plan: which decisions of your lane are implemented, which are missing, and anything outside the plan.
11. Skip style and naming. A copied block of code and hand-written formatting are not style: they break `[review]` rules, so they are P1. Do not suggest new abstractions. Do not edit files.

End with exactly one result line, the last line of your answer, with the counts of the findings above (0 when there are none):

`RESULT lane=<lane> round=<n> P0=<count> P1=<count> user=<count>`

In lane `behaviour` the line ends with the number of items you did not walk: `RESULT lane=behaviour round=3 P0=0 P1=0 user=0 unwalked=0`. A run with an item not walked counts as not run; the finish check also counts every item of the plan's walk list that has no `walked` line in your report as not walked.

with the round as the request names it (`round=3`), and `user` the number of those findings that end with `(for the user)`. When every lane left holds only such findings, the finish check lets the builder stop and wait for the user's answer. The finish check reads this line (docs/workflow.md). A round with no result line counts as not run.
