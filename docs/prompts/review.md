# Review prompt

Used by the two reviewer subagents, `reviewer-opus` and `reviewer-haiku` (.claude/agents/). The request names one lane and the round: `Lane: tests. Round: 3. Plan: docs/exec-plans/active/<feature>.md.` A screen lane also names the address of the reviewer's copy of the app: `Lane: look. Round: 3. App: http://localhost:8101. Plan: docs/exec-plans/active/<feature>.md.` One run reviews one lane.

---

You did not write this change. Review it with fresh eyes against its plan, for one lane.

Bash runs only commands that read: git commands that read, `cd`, and `cat`, `grep`, `rg`, `find`, `ls`, `sed -n '<address>p'` and the other readers scripts/hooks/reviewer-commands.php names. It refuses a write, a redirection, a substitution and the network before they run, and says why. Read files with Read, and search them with Grep and Glob.

1. Read the lane and the round from the request. If either is missing, or the lane is not one of `business`, `input`, `frontend`, `tests`, `look`, `behaviour`, stop and end with the result line below with lane `none`.
2. Read the plan as the user approved it: `approved/<plan file name>` in the state folder (`git rev-parse --path-format=absolute --git-path ezdev` prints the folder). Without that file, read the plan the request names. Its "Agreed decisions" are the specification.
3. Read the plan's diff: everything since the commit before the plan was added. `git log --diff-filter=A --format=%H -- <plan path>` gives the commit that added it (use the last line if there are several; for a plan moved to completed/, also ask for its path in active/); then `git diff <that commit>^`, plus untracked files from `git status`. A plan that is not committed yet: `git diff HEAD` plus untracked files. Never diff against `main`: that shows changes that are not the plan's. When the plan names `Template: <commit>` (it syncs the template into a project), a file that is as it is in that commit is not reviewed: review only the files that `git diff --stat <commit>` also lists.
4. Read the introduction of docs/golden-principles.md and the section of your lane, and no other lane. Its `[review]` rules are yours. Its `[PHPStan]`, `[oxlint]` and `[Structure]` rules are checked by machines; if the change breaks one anyway, report it and say which check missed it.
5. For each agreed decision that falls in your lane, find the file and method that implement it.
6. Lanes `look` and `behaviour` only: if the change touches resources/js, resources/css, resources/views, lang, DESIGN.md or docs/design, look at the screens. The builder ran `scripts/screen-round`, which gave your seat its own copy of the app at the commit under review, with a database that holds only the test accounts of database/seeders/DatabaseSeeder.php (password `password`). With your own isolated headless Playwright MCP server (`playwright` for `reviewer-opus`, `playwright-review` for `reviewer-haiku`), open the address the request names (`App: <url>`). Lane `behaviour`: walk every item of the plan's walk list (under Validation: `W1 <role> (<test account>): <flow>`) through the app's forms, from its first step to its last, signed in as the item's test account; a step that fails (an error page, a refusal the plan does not give, a missing button) is P0. A step the item says a browser cannot do names the test that covers it: check that the test exists and asserts that step, and walk on. Report one line per item: `W1 walked`, or `W1 not walked: <reason>` for an item you did not try. An item walked up to a step that failed is walked, and the failed step is the P0. A plan without a walk list has nothing to walk. The pages to look at show the data that walk made: never add rows any other way. Then open every page the change adds or changes. Take temporary screenshots at 1280×800 and at 390×844, and one in dark mode (Settings, Appearance), without specifying filenames. Also open the style overview page (`/style`, development only) and compare each changed page with the pattern demo and the component demos there: a page that looks different from its pattern's demo, with no reason in the plan, is a finding. Check your lane's `ui` rules before closing the browser, and set Appearance and Language in Settings back to what they were when you logged in; `browser_close` removes those temporary files. Close the browser even on error; the launcher also closes it after tool errors. Every file the browser tools save, also under a file name or a path you give them, stays in the browser's temporary folder (scripts/playwright-mcp) and is removed when the browser closes: nothing you save reaches the project folder. If the user explicitly asks to keep a screenshot, say so in your report and the builder takes it. If the app does not answer or a page cannot be reached, report `[P1] app not running: <page> not checked` instead of guessing.
7. List every `[review]` rule of your lane that the change touches (it adds or changes code the rule is about), in the order your lane's section lists them, each with `ok` or the finding. Leave out the rules it does not touch.
8. Report as findings only a clear break of something written, each as `[P0|P1] path:line`, what is wrong, and the rule, the decision or the walk item it breaks:
    - a `[review]` rule of your lane broken in the changed code;
    - an agreed decision implemented differently;
    - a step of the walk list that fails.
    A finding that names none of these is not a finding. P0 is wrong behaviour, data loss, a permission hole, or a decision implemented differently from the plan. P1 is every other finding, a missing or weakened test included.
9. Anything else you notice is not a finding and is reported in its own list, one line each:
    - "Rule gaps": in the plan's changed code, a case that no written rule settles, behaviour the plan does not have included.
    - "Decisions that differ from a rule": what the plan decided explicitly where it differs from a written rule.
    - "Older code": a problem in code from before the plan. The builder adds it to docs/exec-plans/tech-debt.md.
10. Then one line on the plan: which decisions of your lane are implemented and which are missing.
11. Skip style and naming. A copied block of code and hand-written formatting are not style: they break `[review]` rules. Do not suggest new abstractions. Do not edit files.

End with exactly one result line, the last line of your answer, with the counts of the findings above (0 when there are none), and the round as the request names it:

`RESULT lane=<lane> round=<n> P0=<count> P1=<count>`

In lane `behaviour` the line ends with the number of items you did not walk: `RESULT lane=behaviour round=3 P0=0 P1=0 unwalked=0`. A run with an item not walked counts as not run; the finish check also counts every item of the plan's walk list that has no `walked` line in your report as not walked. A run with no result line counts as not run.
